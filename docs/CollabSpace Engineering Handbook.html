Part 1 — What Is CollabSpace?

The problem it solves: small teams need somewhere to organize work — who's on the team, what projects exist, what tasks are open — without every team's data being visible to every other team using the same app. That "every team's data stays walled off" requirement is called multi-tenancy, and it's the single idea the whole backend is organized around.

Main entities (the nouns your database and API are built around):

Entity What it represents
users An account — one row per person, across the whole app
workspaces A tenant — one company/team's walled-off space
workspace_members The join table: which user belongs to which workspace, and with what role
projects A project inside one workspace
tasks A task inside one project (and, redundantly, tagged with its workspace too — more on why in Part 4)
invitations A pending, token-based invite for someone to join a workspace
refresh_tokens A long-lived credential that lets a logged-in session mint new short-lived access tokens

Main user flows that actually exist in the code (registration → login → create/join a workspace → view projects → view/create tasks → invite teammates). I'm intentionally not calling this "Jira-lite" without qualification yet — Part 3 will show you exactly how much of the task/project management is real vs. still a UI mockup.

Main features, IMPLEMENTED today:

  • Register / log in with email + password
  • JWT access tokens + separate refresh tokens
  • Create a workspace (creator becomes OWNER)
  • Switch between workspaces you belong to
  • List and create projects within a workspace
  • List and create tasks within a project
  • Invite someone to a workspace by email (token-based, expires in 24h)
  • A documented four-role permission model (OWNER/ADMIN/MEMBER/VIEWER) — stored, not yet enforced (flagged properly in the Reality Check section below and covered in depth in Part 7)

Tech stack (confirmed from your package.json files, not assumed):

  • Client: React 19, TypeScript, Vite, React Router, Tailwind CSS v4, lucide-react for icons
  • Server: Node.js, Express 5, TypeScript, Prisma 7 (@prisma/adapter-pg), PostgreSQL, bcrypt, jsonwebtoken, zod

The 30-second version

"CollabSpace is a multi-tenant project-and-task tool — each company gets its own isolated workspace with its own members, projects, and tasks. It's a React/TypeScript frontend talking to an Express/Prisma/PostgreSQL backend, with JWT access + refresh token auth and a role-based permission model that's designed but only partially enforced so far."

The 2-minute version

Add: the entity chain is User → WorkspaceMember → Workspace → Project → Task. The backend is layered — routes hand off to controllers, controllers to services, services to repositories, repositories to Prisma, Prisma to Postgres — specifically so that authorization logic (the "is this user allowed to touch this workspace" check) lives in one place (the service layer) instead of being copy-pasted into every controller. Auth is two-token: a 15-minute JWT access token for normal requests, and a 7-day opaque refresh token stored in the database so it can be revoked on logout. New members join either by being the workspace creator (auto-OWNER) or by accepting an emailed invitation token (currently always as MEMBER).

The 5-minute version

Add: the actual mechanism that makes multi-tenancy work isn't magic — it's one function, verifyWorkspaceMember(), called at the top of every workspace-scoped service method, which does a single-row lookup against workspace_members on the compound key (user_id, workspace_id). No row → 403 Forbidden. That's it — that's tenant isolation in this codebase. Tasks additionally carry their own workspace_id column even though they already belong to a project (which itself belongs to a workspace) — that's a deliberate denormalization so a task query never has to join through projects just to check which tenant it belongs to. And here's the honest, interview-relevant gap: your own docs/RBAC-permission-matrix.md describes four roles with different permissions, but verifyWorkspaceMember() only checks membership, never role. A VIEWER today can hit the same create-project endpoint as an OWNER. That's the single most important "documented vs. real" gap in the project, and Part 7 is going to be built around it.

    B --> C[Express Route]
    C --> D["Middleware (requireAuth, validateBody)"]
    D --> E[Controller]
    E --> F[Service]
    F --> G[Repository]

Now let's trace real ones, file by file.

Request 1 — Registration

POST /auth/register  { name, email, password }
  → app.ts:            app.use("/auth", authRouter)
  → auth.routes.ts:     validateBody(RegisterSchema) → register()
  → validateBody.ts:    RegisterSchema.safeParse() — name non-empty, valid email, password ≥ 8 chars

  → auth.service.ts:    registerUser()

Request 2 — Login

sequenceDiagram
    participant C as Client
    participant Route as auth.routes.ts
    participant Ctrl as auth.controller.ts

Notice loginUser returns the same generic unauthorized("Invalid email or password") whether the email doesn't exist or the password is wrong — that's deliberate; it stops an attacker from using your login endpoint to figure out which emails are registered.

Request 3 — Create Workspace

POST /api/workspaces  { name }   Authorization: Bearer <accessToken>
  → workspace.routes.ts:  requireAuth → validateBody(CreateWorkspaceSchema) → createWorkspace()
  → requireAuth.ts:       jwt.verify() → req.user = { id: decoded.sub }
  → workspace.controller: reads req.user.id + req.body.name
  → workspace.service:    createWorkspaceService() — name.trim() === "" ? badRequest : createWorkspaceWithOwner()
  → workspace.repository: createWorkspaceWithOwner(userId, name)

// workspace.repository.ts — this is a good pattern, worth internalizing
export async function createWorkspaceWithOwner(userId: string, name: string) {
  return prisma.$transaction(async (tx) => {
    const workspace = await tx.workspaces.create({ data: { name } });
    const membership = await tx.workspace_members.create({
      data: { user_id: userId, workspace_id: workspace.id, role: "OWNER" },
    });
    return { workspace, membership };
  });
}

The $transaction matters: without it, a crash between "create the workspace" and "create the membership row" would leave an orphaned workspace nobody can access. Wrapping both in a transaction makes them atomic — either both happen or neither does.

Request 7 — Unauthorized Request

Three distinct failure modes, each mapping to a different HTTP status — this is a great interview answer on its own:

Scenario Where it fails Status Why
No Authorization header requireAuth.ts, before the route even runs 401 We don't know who you are
Expired / malformed JWT requireAuth.ts — jwt.verify() throws, caught, rethrown as unauthorized("Invalid or expired token") 401 We can't confirm who you are
Valid token, but not a member of the target workspace verifyWorkspaceMember() in the service layer 403 We know exactly who you are — you're just not allowed here

That 401-vs-403 split ("who are you" unresolved vs. "we know, but no") is exactly the distinction between authentication and authorization, and CollabSpace draws that line cleanly across two different layers of the stack (middleware vs. service).

Every primary key is a String @db.Uuid generated via Postgres's own gen_random_uuid() (the pgcrypto extension is enabled in 001_create_users.sql) — so IDs are generated by the database, not the application.

Why the redundant workspace_id on tasks? A task already belongs to a project, and a project already belongs to a workspace — so workspace_id is technically derivable by joining through projects. Storing it directly on tasks anyway is a deliberate denormalization: every tenant-scoped task query (which is most task queries) can filter on workspace_id directly instead of joining through projects first, and it's what makes the idx_tasks_workspace_id index actually useful. This is a good, defensible tradeoff — not an oversight.

Why Postgres: the domain is genuinely relational — memberships, ownership chains, and cascading deletes (delete a workspace → its projects and tasks should go with it) are exactly what foreign keys and ON DELETE CASCADE exist for.

Why Prisma: type-safe query building that matches a TypeScript-heavy stack, with types generated straight from the schema instead of hand-maintained.

Where migrations actually happen — and a real inconsistency worth knowing about. Your repo has hand-written SQL files under server/src/db/migrations/*.sql (six of them), and separately, prisma.config.ts points Prisma at a prisma/migrations folder — but no files exist there in what you uploaded. That strongly suggests schema changes are currently driven by the raw SQL files, with schema.prisma kept in sync by hand rather than by prisma migrate dev. (I can't verify this with full certainty from the files alone — if you do use prisma migrate, let me know and I'll correct this.) One small, concrete bug in those SQL files: there are two files numbered 004 — 004_add_indexes.sql and 004_create_tasks.sql. Harmless today, but any tool that applies migrations by sorting filenames would have an ambiguous order between them.

Part 5 — Authentication Deep Dive

Part 3 already traced registration and login file-by-file. This section goes one level deeper: what's actually inside the tokens, and the precise line where authentication hands off to authorization.

Concept: The Access Token

What is it? A signed JSON Web Token proving "this request comes from an already-authenticated user," valid for a short window.

Actual code:

// auth.service.ts — signing, at login
const accessToken = jwt.sign({ sub: user.id }, jwtSecret, { expiresIn: "15m" });

// requireAuth.ts — verifying, on every protected request
const decoded = jwt.verify(token, jwtSecret) as JwtPayload; // JwtPayload = { sub: string }
req.user = { id: decoded.sub };

What's actually inside it: just { sub: <userId> }, plus the standard iat/exp claims jsonwebtoken adds automatically. No name, no email, no role — anything else a controller needs, it looks up fresh from the database using req.user.id.

How it's signed: HS256 (HMAC, one shared secret — JWT_SECRET), not RS256. That's the right call for a single backend service that both signs and verifies its own tokens; RS256 earns its complexity when a different service needs to verify tokens without being trusted to issue them.

Why 15 minutes? Short enough that a leaked token is only dangerous for a small window — and short enough that you need a refresh mechanism for any real session, which is exactly why the next concept exists.

Failure case: malformed signature, wrong secret, and expired token all hit the same catch in requireAuth.ts and return the identical response:

try {
  const decoded = jwt.verify(token, jwtSecret) as JwtPayload;
  ...
} catch {
  throw unauthorized("Invalid or expired token"); // 401 — no distinction given to the client
}

Not distinguishing the failure reason to the client is a defensible security default, whether or not it was consciously chosen.

Alternative: server-side session cookies instead of JWTs. Trade-off: cookies need a shared session store (or sticky sessions) across multiple server instances; JWTs are stateless — any instance can verify one alone — but can't be revoked before they expire. That gap is exactly what the refresh token below is for.

Interview question: "What's inside your JWT, and what would you never put in it?" — Answer: just the user ID; never a password, never a role (unless you're fine with it being stale for up to 15 minutes), never anything sensitive — the payload is base64-encoded, not encrypted.

Practical exercise: decode one of your own access tokens at jwt.io and confirm it really only carries sub, iat, exp.

Concept: The Refresh Token

What is it? A long-lived, opaque, revocable credential that mints new access tokens without re-entering a password.

Actual code:

// auth.service.ts
function generateRefreshToken() {
  return crypto.randomBytes(32).toString("hex"); // opaque — NOT a JWT
}

// refreshToken.repository.ts
export async function createRefreshToken(userId, token, expiresAt) {
  return prisma.refresh_tokens.create({ data: { user_id: userId, token, expires_at: expiresAt } });
}

Why opaque instead of a JWT? It's checked against the database on every use anyway (findRefreshToken), so there's no benefit to making it self-describing — and a random string leaks zero information if intercepted, unlike a JWT payload.

Where it's stored: server-side, in refresh_tokens (user_id, unique token, expires_at, nullable revoked_at). Client-side storage isn't visible anywhere in the uploaded frontend — consistent with the earlier finding that no login flow exists in the client code at all.

Expiration: 7 days. Revocation: yes — revoked_at is set by revokeRefreshToken(), called from logoutUser(), and both expiry and revocation are checked on every refresh:

if (storedToken.revoked_at) throw unauthorized("Invalid refresh token");
if (storedToken.expires_at <= new Date()) throw unauthorized("Invalid refresh token");

Rotation: NOT implemented. refreshAccessToken() issues a new access token but never issues a new refresh token and never revokes the old one. Name this precisely in an interview, not just as "it's insecure": if a refresh token is ever stolen, it stays fully valid for the rest of its 7-day life — usable by the attacker and the real user simultaneously — with nothing in the current code to detect or interrupt that. The standard fix, rotation, would issue a brand-new refresh token on every use and immediately revoke the one just spent, turning a stolen-and-reused token into a detectable collision.

Interview question: "Why not skip refresh tokens and just use a longer-lived JWT?" — Because a JWT can't be revoked before it expires. The refresh-token pattern buys you a revocation lever at the cost of one extra round trip.

Practical exercise (good Phase 15 candidate): implement rotation — on every successful /auth/refresh, revoke the incoming token and create + return a new one alongside the new access token.

Authentication vs. Authorization, precisely located in your code

Authentication = Who are you?      →  requireAuth.ts          (route-level, generic, runs first)
Authorization  = Are you allowed?  →  verifyWorkspaceMember()  (service-level, resource-specific, runs second)

requireAuth never looks at which workspace/project/task is being touched — it only confirms the JWT and sets req.user.id. verifyWorkspaceMember never re-checks the JWT — it trusts req.user.id is already legitimate and asks a narrower question: does this person have any relationship to this resource? Different questions, different layers — which is exactly why one produces 401 and the other 403.

Part 6 — Tenant Isolation Deep Dive

A "tenant" here is a workspace. Every project and task belongs to exactly one, and the whole security model exists to guarantee a user can only ever reach data belonging to a workspace they're actually in.

Concept: verifyWorkspaceMember()

Actual code:

// project.service.ts — identical pattern in task.service.ts
async function verifyWorkspaceMember(workspaceId: string, userId: string) {
  const membership = await findWorkspaceMembership(workspaceId, userId);
  if (!membership) {
    throw forbidden("You are not a member of this workspace");
  }
}

// workspace.repository.ts
export async function findWorkspaceMembership(workspaceId: string, userId: string) {
  return prisma.workspace_members.findUnique({
    where: { user_id_workspace_id: { user_id: userId, workspace_id: workspaceId } },
  });
}

Inputs: workspaceId (from the URL/query — always attacker-controllable, never trust it blindly) and userId (from req.user.id, set by requireAuth from the verified JWT — this one is trustworthy).

Database query: one indexed lookup on the compound unique key (user_id, workspace_id) — O(1), not a scan.

Result → failure → response: null → throw forbidden(...) → caught by errorHandler → 403.

What happens after success: nothing extra — the function returns void and the caller proceeds. Notice what it doesn't do: it fetches the whole row, including .role, and discards it. That discarded field is exactly where RBAC hooks in (Part 7).

Why this design holds up even with the RBAC gap: the check lives in one function per resource type, called from every service method that touches it — not copy-pasted into a dozen controllers. Closing the RBAC gap means adding one more check inside (or right after) this function, not hunting for call sites.

Failure case today: nothing forces a developer adding a new route to remember to call this. It's a convention, not something the framework enforces.

Practical exercise: add a console.log right after the membership lookup and confirm, against your own running server, that a mismatched pair short-circuits before any Prisma write happens.

Part 7 — RBAC Deep Dive

You mentioned you're building this right now, so this section stays diagnostic — what exists, precisely, today — rather than solving it for you. You'll get more out of writing the check yourself than reading mine.

The four documented roles vs. what the code can actually produce:

Role In RBAC-permission-matrix.md? Ever actually assigned in code?
OWNER Yes Yes — createWorkspaceWithOwner()
ADMIN Yes No — no code path writes it
MEMBER Yes Yes — acceptInvitationService()
VIEWER Yes No — no code path writes it

Only two of the four designed roles are reachable through the app at all today. role is a plain string column with no database-level enum — nothing stops ADMIN/VIEWER from being written, but nothing currently does.

Permission matrix — designed vs. actually enforced:

Action Designed Actually enforced today
View workspace / projects All roles Any member — role never checked
Create project Owner, Admin, Member Any member, including a hypothetical Viewer — role never checked
Update / delete project Owner, Admin (+Member for update) Not implemented — no route exists
Create task Owner, Admin, Member Any member — role never checked
Update / delete task Owner, Admin, Member Not implemented — no route exists
Invite member Owner, Admin Any member — role never checked
Remove member / change role Owner, Admin Not implemented — no route exists
Delete workspace / transfer ownership Owner only Not implemented — no route exists

Is there a requireRole? No — no such file under middleware/, and no .role comparison in any controller or service. The only place .role is read (not written) is the response mapping that lets WorkspaceSwitcher/Badge display it on the frontend — cosmetic, not a gate.

Where would enforcement hook in? The natural seam is inside or right after verifyWorkspaceMember() — it's already holding the membership row, .role included, before throwing it away. A role check needs: the membership row (already fetched), a way to express "this action needs at least role X," and an ordering of the four roles so OWNER satisfies anything ADMIN does.

Why frontend-only checks would never be enough, concretely here: hiding the "New Project" button for a Viewer in React doesn't stop that Viewer from copying your apiFetch call and hitting POST /api/workspaces/:id/projects directly with their own valid token — which, per the table above, currently succeeds, because the backend never asks what their role is. Enforcement has to live where the request lands, not just where the button is drawn.

Interview question: "Your docs say Viewers can't create projects. Can they, right now?" — "Not by design, but yes, technically, today — the check only verifies membership, not role. That's the exact gap I'm closing, and I know exactly which function it goes in."
