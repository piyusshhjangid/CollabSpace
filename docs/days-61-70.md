# CollabSpace roadmap: Days 61–70

This increment adds measured project-summary caching, ephemeral workspace presence, multi-instance Socket.IO fanout, durable request idempotency, authentication throttling, and a separate invitation-email worker. PostgreSQL remains the source of truth for application records and idempotency responses. Redis holds disposable cache/presence state and BullMQ queue state.

## Day 61–63: summary cache and measurement

Start Redis from the repository root with `docker compose up -d redis`, then set `REDIS_URL=redis://localhost:6379` in `server/.env`. Restart the API after changing `SUMMARY_CACHE_DISABLED`.

The summary route returns `X-Summary-Cache: HIT | MISS | BYPASS` and `X-Summary-Elapsed-Ms`. Cache keys include the workspace ID, project ID, and a workspace generation. Task creation/updates, project creation/deletion, and outcome changes increment the generation; stale generations expire naturally. Summary entries have a 30 second TTL. A Redis outage bypasses cache reads/writes and loads from PostgreSQL. The authenticated `GET /api/projects/summary/metrics` endpoint reports in-process hit ratio and rolling p50/p95 timing samples; `npm run benchmark:summary` measures end-to-end API timings.

| Condition | Project summary | Presence / Socket.IO | Auth limits | Email queue |
| --- | --- | --- | --- | --- |
| Redis configured and healthy | Cache hit/miss; PostgreSQL is the source on a miss | Presence and cross-instance room fanout enabled | Shared per-IP and per-email windows | Durable BullMQ enqueue, when SMTP is configured |
| Redis missing or unavailable | Bypass cache and read PostgreSQL | Presence is unavailable; sockets still work in one instance | Process-local fallback (not shared between API instances) | Invitations still work by token; no email enqueue if unavailable |
| PostgreSQL unavailable | API request fails; cached summary is not served as authoritative data | Socket workspace join is rejected | Auth flows requiring PostgreSQL fail | Worker cannot verify invitation state or mark delivery |

For a comparable baseline and cached report, in PowerShell set `WORKSPACE_ID`, `PROJECT_ID`, and `ACCESS_TOKEN` to a real workspace/project and a valid access token. Then:

1. Set `SUMMARY_CACHE_DISABLED=true` in `server/.env`, restart the API, then run `$env:RESULT_FILE='../docs/summary-baseline.json'; npm run benchmark:summary` from `server`.
2. Set `SUMMARY_CACHE_DISABLED=false`, restart the API, run the same benchmark with `$env:RESULT_FILE='../docs/summary-cached.json'`.
3. Compare p95 and cache hit ratio. Use the same account, project, warmup, and iteration count. The benchmark is intentionally opt-in; no performance claim is recorded until it is run against a reachable PostgreSQL/Redis instance.

`SUMMARY_CACHE_DISABLED=true` bypasses Redis but retains response timing headers so the same route and auth path are measured. Benchmark reports contain timing/cache counts only, not access tokens or response bodies.

## Day 64–65: presence and multi-instance sockets

An authenticated socket must join a workspace after PostgreSQL membership validation. The client sends a heartbeat every 10 seconds. Redis stores socket heartbeats in a workspace sorted set; entries older than 30 seconds are removed whenever presence is refreshed. Socket leave/disconnect removes the entry immediately. Redis failure only disables presence and does not disconnect the realtime channel.

The Socket.IO Redis adapter is enabled when `REDIS_URL` is configured. For multiple API instances behind a load balancer, enable sticky sessions at the proxy/load balancer while Socket.IO polling is enabled, and route WebSocket upgrades to the same instance. The Redis adapter distributes room events; it does not replace sticky sessions for Engine.IO polling. Without Redis, the API uses its local adapter and only delivers between sockets on the same instance.

## Day 66–67: request idempotency and auth limits

`POST` project and task creation accept an `Idempotency-Key` (8–200 characters). CollabSpace clients create a UUID key for each user action. PostgreSQL stores the user/key pair, request hash, response status, and response JSON; an identical replay returns the original response. Reusing a key with a different body returns `409`. Concurrent requests receive `409` and `Retry-After: 1`. Incomplete rows older than five minutes can be reclaimed; completed rows are pruned after 24 hours. A caller that needs to retry after a connection loss should reuse the original key.

Login and registration are limited per source IP and normalized email, using Redis fixed windows. They return `429` with `Retry-After` and `RateLimit-*` headers. If Redis is unavailable, a process-local fallback keeps one-instance development usable; its counters are not shared across API instances, so restore Redis for distributed enforcement.

## Day 68–70: notification worker, retries, and DLQ

Invitation emails are enqueued after invitation creation when both Redis and `SMTP_HOST` are configured. The API does not send email inline. Start a separate process from `server` with `npm run worker`; configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, optional `SMTP_USER`/`SMTP_PASSWORD`, `EMAIL_FROM`, and `APP_BASE_URL`. If email is not configured, invitations continue to work through the existing token flow and no email job is created.

The `notifications` queue uses five attempts with exponential backoff starting at one second. A job that exhausts retries is copied to `notifications-dlq`; inspect it with `npm run jobs:dead-letters`. The listing deliberately omits recipient addresses and invitation tokens. Remove/replay DLQ entries only after correcting the cause; queue state is in Redis and should be protected and backed up for production.

Invitation job IDs are deterministic (`invitation-<invitation UUID>`), and messages carry a deterministic Message-ID. The worker checks PostgreSQL's `email_sent_at` before sending and records successful sends. This prevents normal duplicate enqueues and completed retries from sending again. SMTP is at-least-once: a process can fail after the provider accepts an email but before PostgreSQL records success, so the stable Message-ID is a best-effort dedupe hint and a rare duplicate delivery remains possible.

## Migration and operational notes

Before deploying this code, run `npm exec prisma migrate deploy` and `npm exec prisma generate` from `server` after `DATABASE_URL` points to a reachable PostgreSQL instance. The migration adds the PostgreSQL idempotency ledger and invitation email delivery timestamp. Keep `.env` private; `.env.example` lists the new settings.
